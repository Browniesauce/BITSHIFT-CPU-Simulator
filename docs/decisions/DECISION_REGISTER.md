# BITSHIFT — Decision Register

**Status:** Living document. Phase 0 review item.
**Purpose:** The single list of decisions that shape BITSHIFT, with origin and status. Nothing here is final unless it is category **A**, or its status is **Approved**.

## Categories and Status Vocabulary

| Cat.  | Meaning                                                                          | Status vocabulary                                                                        | Who decides                           |
| ----- | -------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------- | ------------------------------------- |
| **A** | Established by the product owner (stated as a requirement or fact in the brief). | Established                                                                              | Already decided                       |
| **B** | Proposed engineering decision, written into the Phase 0 documents as a proposal. | Proposed → Approved (optionally qualified)                                               | Product owner approves                |
| **C** | Unresolved question. Needs an answer before the dependent work starts.           | Open → Answered, Approved (qualified or amended), or Partially approved; or **Deferred** | Product owner, with engineering input |

- **Approved (qualified):** approved with conditions. The conditions are recorded in the same row.
- **Answered:** the question has been answered by another decision. The answer is recorded in the row.
- **Deferred:** recognised and intentionally not decided yet. It must not be started until its trigger, stated in the row, occurs.

A proposal becomes **Approved** only when the product owner says so. Record every change in the change log at the bottom.

## D. Reconciliation Findings (Stage 0.2 closeout)

These findings record what each open item still depends on. They do not answer the questions.

### R-01 — DR-011 (cycles and micro-operation sequence per instruction)

- **Still unresolved:** the cycle count for each instruction; the micro-operation sequence for each instruction; whether a 2-byte instruction's operand fetch is separate cycles; whether cycle count depends on data (for example JZ taken or not taken); whether HLT and a fault consume a cycle.
- **Affects clock-level execution through:** DR-002 (unified memory means fetch and data access may share the address path), DR-004 (PC wrap during fetch), DR-010 (LDI encoding changes the sequence), DR-012 (mnemonics without opcodes), DR-016 (HLT and fault), DR-018 (step boundaries), DR-005 (display-only registers used as micro-operation endpoints), DR-006 (OUT).
- **Affects control-signal visualization (MVP-019) through:** DR-011 (which signals exist in each step), DR-013 (their representation), DR-023 (bus model, which determines bus-transfer signals), DR-051 (which signals are shown).
- **Needed before Phase 2:** DR-001 to DR-018 closed; a sequence for each of the 20 mnemonics; DR-013 internal representation fixed (Phase 2 stage 2.4 entry).
- **Safe for Stage 0.3:** the generic envelope: cycle as the step unit, sequence within a cycle, before and after values on state changes, and a `controlSignals` list supplied by the architecture. None of these depend on BITSHIFT-8 values.
- **Not safe for Stage 0.3:** concrete signal names, micro-operation vocabulary, cycles per instruction, and timeline cycle numbering for branches.
- **Not invented:** no cycle counts or sequences have been proposed in this review.

### R-02 — DR-013 (micro-operation representation)

- The question combines two concerns: (a) how an architecture represents micro-operations internally (typed objects, strings, functions); and (b) what the platform sees (the shared event payload).
- DR-053 (approved) already settles part of (b): micro-operation events carry control-signal names.
- Still open for (b): the payload fields beyond control signals (label, sources, destinations), and the before and after requirement for flag and output events. Stage 0.3 can define these generically.
- Still open for (a): the internal representation is private to the architecture and is not part of the shared contract. It is needed only at Phase 2 entry.
- **Status after final approval:** `controlSignals` is approved. `label`, `sources` and `destinations` are deferred to Phase 2. The internal representation remains open and is the only part that blocks Phase 2 (DR-013 partially approved).

### R-03 — DR-031 (performance targets)

- Two different measures are combined: (1) a UI frame budget (one micro-operation updates the UI within one frame), measurable only in Phases 4 and 5; and (2) core throughput (10,000 instructions in under 2 s with animation paused), measurable headless in Phase 1.
- "Typical laptop" has no reference definition. The product owner must define a reference machine.
- It is unclear whether measure (2) includes snapshot copying, event delivery and history recording. The recommendation is that it does, so the measure covers the full core.
- A 10,000-instruction run fills the default history limit (DR-024) exactly. Confirm that this is intended.
- **Stage 0.3 blocker:** none. The contracts do not depend on these numbers. DR-056 requires measurement during implementation.

### R-04 — DR-045 and MVP-022 (instruction explanations)

- **Requirement strength:** the brief lists "instruction-level explanations where practical". That is conditional, not a hard requirement. Journey step 10 can be met in part by the MVP-021 change list.
- **Acceptance criteria:** AC-022-1 (a template for every instruction) and AC-022-2 (names the registers and flags changed) are testable. Missing: the fallback when a template is absent (DR-061 requires generic text and no blocking); the one-line format; whether the explanation is per instruction or per micro-operation (proposal: per instruction, on the timeline entry); and language (English, DR-050). Proposed additions: AC-022-3, breaking every template leaves execution results unchanged (test); AC-022-4, a missing template shows generic text (test).
- **Stage ownership:** Stage 5.4 already covers "entry detail", which fits displaying the explanation. Writing the templates is architecture content, one per instruction, and belongs to Stage 2.3 (instruction table). Assigning all of it to Stage 5.4 would hide Phase 2 work inside a UI stage.
- **Scope:** a new stage would break A-13 (32 stages). Using Stages 2.3 and 5.4 keeps the count.
- **Status after final approval:** DR-045 approved for v1.0 with limited scope (SC-D5). Stage 2.3 authors the explanations; Stage 5.4 displays them with generic fallback. Roadmap and MVP traceability are updated accordingly.
